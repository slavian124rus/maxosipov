## Найденные проблемы

### Средние

**F1. Автообновление фото не включалось (исправлено).**
Пока воркер не взял файл, медиа в статусе `uploaded`; интерфейс считал «в обработке» только `processing` и не запускал опрос. «Обрабатывается…» висело, пока пользователь не перезагрузит страницу (e2e на этом и застрял).
Исправление: в `listProgressPhotos` любой статус, кроме `ready`/`failed`, отдаётся как `processing`; тест «фото в очереди (uploaded)».

**F2. Доступ к файлу фото не учитывает «чей клиент».**
`assertCanAccessMedia` для `progress_photo` проверяет только `can(actor, 'clients.view_photos')` без контекста клиента, поэтому тренер с правом в области «только свои» может открыть файл чужого клиента, если знает id медиа (uuid, подписанные ссылки выдаёт только `listProgressPhotos`, так что случайно не угадать).
*Как исправить:* найти владельца через `progress_photos`/`media.ownerId`, взять его `trainerId` и вызвать `can(actor, 'clients.view_photos', { clientId, clientTrainerId })`.

### Низкие

**F3. `addProgressPhoto` не проверяет дату.** Дата приходит из формы (`formData.get('date')`): можно прислать будущую или кривую строку, пользователь увидит техническую ошибку БД. Нужен тот же `assertDateRange`, что у замеров. Поза проверяется в экшене, но не в сервисе.

**F4. Фото привязывается к недозагруженному файлу.** Сервис не проверяет, что загрузка завершена (`originalPath` есть). Последствие мелкое (останется «Обрабатывается…»), но стоит отказывать явно.

**F5. HEIC не поддержан** (отклонение от плана, описано в отчёте). Нужна проверка на реальном iPhone.

**F6. Нет внешних ключей** у `body_measurements` и `progress_photos` на `users`/`media`: при удалении пользователя строки останутся. Если принято хранить без FK — оставить, иначе добавить `ON DELETE CASCADE`.

### Тесты

- `e2e/progress.spec.ts` почищен (отладочные логи, фиксированная пауза, убийство воркера через группу процессов).
- В `workout.spec.ts` добавлено ожидание гидратации: в prod клик по «Записать подход» иногда терялся.

## Исправления выполнены (по просьбе владельца)

- **F2:** `assertCanAccessMedia` определяет владельца фото и проверяет `clients.view_photos` с учётом «чей клиент». Заодно закрыто: догружать куски и завершать загрузку чужого фото нельзя (`{ write: true }` в роутах `chunk`/`complete` пускает только владельца).
- **F3:** `addProgressPhoto` проверяет формат даты, диапазон (не в будущем, не старше 5 лет) и позу.
- **F4:** файл со статусом `uploaded` без исходника не привязывается («Фото ещё загружается»).
- Тесты: даты/поза, недогруженный файл, доступ «только свои» и запись в чужой файл. `pnpm verify` — 339 тестов; e2e прогресса — 5/5.
- **F5, F6 не меняли.** F6: между модулями в проекте внешних ключей нет (так устроены и тренировки), поэтому удаление пользователя должно чистить данные явно. F5 требует реального iPhone.
