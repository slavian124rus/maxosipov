## Найденные проблемы

### Критичные

**F1. Подходы не отображаются в интерфейсе.**
`workout-client.tsx` хранит `logged` по ключу `exercise.exerciseId`, а `FreeMode`/`GuidedMode` читают
`logged[exercise.programExerciseId]` (это другой uuid). Подтверждено в браузере: после «Записать
подход» чипа «1: … кг · … раз» нет, счётчик подходов не растёт, «Как прошло упражнение?» и карточка
«В следующий раз» **никогда не появляются** (`complete` не наступает). Тот же ключ при восстановлении
из Dexie. Итог тренировки считается верно только потому, что считает по `exerciseId`.
*Как исправить:* один ключ везде — `programExerciseId`; в `log()`/`restore` использовать его же.
Добавить e2e (см. F11).

**F2. Возобновление тренировки не работает (Review Focus №2).**
`boot()` в `WorkoutClient` запускается на монтировании, когда `session.session` ещё `null`
(хук читает Dexie асинхронно), и поэтому **всегда** вызывает `start()` и создаёт новую сессию
поверх активной. Проверено: после перезагрузки появляется третья сессия в БД, старая брошена
незавершённой. Это не связано с Dexie.
*Как исправить:* в `boot()` сначала читать `activeSession` из Dexie напрямую; `start()` — только если
записи нет (и её `programDayId` совпадает с днём страницы). Дождаться загрузки хука, а не читать
state из замыкания.

**F3. «Блокер Dexie» — это отсутствующий индекс.**
`sets: 'clientUuid, synced'`, а запросы идут `where('sessionClientUuid')`. Dexie падает с
`SchemaError` (`KeyPath … is not indexed`) — именно это видно как `pageerror: DexieError` в
браузере. Turbopack/импорт/SSR ни при чём; в Node тесты зелёные, потому что `where('sessionClientUuid')`
в них не вызывается. Резервное хранилище в памяти ошибку **не ловит** (ошибка возникает при запросе,
а не при создании Dexie) и скрывает часть проблемы, при этом лишний код `createMemoryDb`
(~90 строк) — опасная заплатка.
*Как исправить:* `db.version(2).stores({ activeSession: 'clientUuid', sets: 'clientUuid, synced, sessionClientUuid', feelings: '++id, sessionClientUuid, synced' })`
(версия 2 — у разработчиков база v1 уже создана). Удалить `createMemoryDb` и `try/catch` с
подменой. Тест очереди на `where('sessionClientUuid')` в `fake-indexeddb`. **Менять на `idb` не нужно.**

**F4. Старт тренировки без сети никогда не досылается.**
`/api/training/start` вызывается один раз при старте и не повторяется. Если сети не было,
`syncSets` на сервере кидает «Тренировка не найдена», роут отвечает 400, `flushQueue` считает всю пачку
`failed` — и так вечно: подходы застревают навсегда. Это ровно сценарий «в зале плохая связь».
*Как исправить:* флаг `startSynced` в `activeSession`; `flush()` сначала досылает старт (идемпотентный),
потом подходы. Либо `syncSets` создаёт сессию по `sessionClientUuid` + `programDayId`/`startedAt`, если её нет.

**F5. Завершение тренировки теряется офлайн.**
`finish()`: ошибка сети/не-2xx глотается, затем `activeSession.clear()` — сессия на сервере остаётся
`finished_at = null`: не попадает в историю «Тренировки», серию недели и «следующий день».
*Как исправить:* помечать `finishRequestedAt` локально, чистить `activeSession` только после успешного
ответа; повторять в `flush()`. Проверять `response.ok`.

**F6. Очередь живёт только пока открыт экран тренировки.**
Таймер 15 с и `online` повешены на хук внутри `/workout`. После «Завершить» → переход на «Сегодня» —
несинхронизированные подходы никто не отправляет до следующей тренировки.
*Как исправить:* глобальный синхронизатор в корневом клиентском layout приложения (одно место),
плюс `visibilitychange`.

**F7. Видео офлайн не кэшируется в production.**
В `@serwist/turbopack` `defaultCache` в production содержит перехватчик «все same-origin, кроме
/api» (`NetworkFirst`, кэш `others`). Он зарегистрирован раньше правила `/media/*`, поэтому
CacheFirst для видео **не срабатывает**; в dev `defaultCache` = `NetworkOnly`, поэтому в разработке
это не заметно. Дополнительно: нет `RangeRequestsPlugin` (iOS Safari требует 206 для `<video>`),
а `precacheMedia` нигде не вызывается — предзагрузка программы не реализована.
*Как исправить:* регистрировать правило для `/media/` **до** цикла по `defaultCache`; добавить
`RangeRequestsPlugin`; вызвать предзагрузку при открытии `/workout`; проверить в production-сборке
(`pnpm build && pnpm start`, DevTools → Application → Cache Storage, офлайн-режим).

### Серьёзные

**F8. Один «битый» подход блокирует всю очередь.**
`syncSets` падает на первой же ошибке (нет сессии, чужой `exerciseId`, NaN), роут возвращает 400 на всю
пачку, `flushQueue` повторяет её каждые 15 с бесконечно. *Исправить:* валидация Zod на роутах
(вес 0–1000, повторения 1–200, `setIndex` ≥ 1, uuid, ≤ 50 элементов); принимать элементы по одному
и возвращать `accepted` + `rejected`; отклонённые помечать на клиенте как `failed` и не слать повторно.

**F9. Перезапись чужого подхода по `client_uuid`.**
`onConflictDoUpdate` по `clientUuid` не проверяет владельца: пользователь, отправивший подход с чужим
`clientUuid`, перезапишет вес/повторения чужой записи (владелец сессии проверяется только у **своей**
сессии). *Исправить:* в `set` и `where` — `set_logs.session_id = excluded.session_id`
(иначе пропустить/ошибка); тест на этот случай.

**F10. Ощущение стирается повторной отправкой и не доходит офлайн.**
(а) upsert пишет `feeling: item.feeling ?? null` — повтор подхода (ответ потерялся) сбрасывает ощущение,
выставленное через `setExerciseFeeling`. (б) `setFeeling` шлёт запрос один раз, ошибка глотается;
таблица `feelings` в Dexie не читается нигде; если подходы уже `synced: 1`, локальный `modify({feeling})`
их не переотправит. *Исправить:* `feeling` в upsert — `coalesce(excluded.feeling, set_logs.feeling)`;
очередь ощущений в `flush()` с пометкой `synced`.

**F11. Нет e2e тренировки (план, задача 5, шаг 6).**
Именно поэтому F1–F6 не поймали. Нужны: (а) день A в выбранном режиме → подходы видны → «Легко» →
«В следующий раз» → завершить → сессия в БД `finished_at not null`; (б) офлайн после старта, перезагрузка,
подходы на месте, `setOffline(false)` → в БД за ≤ 20 с; (в) старт **офлайн**; (г) хост редиректа после
входа (обещанный в отчёте тест на поддомен).

**F12. Сид на чистой БД не выдаёт программы.**
Шаблон создаётся до пользователей — клиенты 1–4 получают программу только со **второго** запуска сида.
Проверено: после `db:migrate && db:seed` у клиента «Привет, Иван» → «Максим скоро подберёт тебе программу».
*Исправить:* выдачу делать после `ensureUsers`.

### Средние

**F13.** `applyProgramPatchAs` читает `getProgramTree` и `publishedExerciseIds` через глобальный `db`, а не
`tx` — работает только благодаря блокировке, занимает лишние соединения пула. Передавать `tx`.

**F14.** Нет ограничения «одна активная программа на клиента» (частичный unique-индекс
`(owner_id) where status='active'`); два параллельных `copyTemplateToClient` создадут две активные.

**F15.** Нет индексов: `set_logs(session_id)`, `set_logs(exercise_id)`, `workout_sessions(user_id, started_at)`.
`getHistoryForExercise` забирает **всю** историю и режет `limit` в памяти, а `getRecommendations` вызывает его
для каждого упражнения (N+1). Ограничить в SQL (последние N сессий) и добавить индексы.

**F16.** `weight_kg real` (float4): 62,3 вернётся как 62.29999… Нужен `numeric(6,2)` или `double precision`,
иначе сравнения весов и вывод ломаются.

**F17.** API-роуты не ловят `ForbiddenError` от `assertClientAccess` → 500 вместо 403; при истёкшей
подписке посреди тренировки клиент будет бесконечно получать 500. `next-weight` и `start` без валидации
(`startedAt` → `Invalid Date`, нет проверки `exerciseId`/`programDayId` принадлежности). `startSession` — гонка
двух параллельных вызовов: нужен `onConflictDoNothing`.

**F18.** `finishSession` не идемпотентна (повтор перезаписывает `finishedAt` и ставит ещё одну задачу).
В `getRecommendations`/`getWeekWorkoutDays` часовой пояс `Asia/Krasnoyarsk` зашит в код — брать из настроек зала;
`getWeekWorkoutDays` читает все завершённые сессии за всё время.

### Интерфейс и тексты

**F19.** Пошаговый режим: видео `aspect-[9/16]` на 375 px занимает весь экран, «Старт подхода» уходит за
экран — нужен ограниченный размер (например, 4:5 или `max-h` около 45% высоты).
**F20.** Вес в чипах и степпере выводится как `32.5 кг` — по правилам текста «32,5 кг» (есть `formatWeight`).
**F21.** Свайп в пошаговом режиме не сделан (отклонение указано в отчёте — принято условно); нет возможности
исправить/удалить записанный подход и добавить лишний.
**F22.** Опрос `program-version` раз в 30 с и плашка «Максим обновил программу» (задача 5, шаг 5) в коде
не найдены — роут есть, клиента нет. Статус в отчёте «сделано» неверен.
**F23.** Незавершённые подходы не очищаются: после завершения таблицы `sets`/`feelings` в Dexie остаются.
**F24.** `nextWeight()` — `fetch` без `catch` и без очереди: офлайн даёт необработанное исключение и теряет выбор.
